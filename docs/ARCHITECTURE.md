# Architecture

KubeSage follows **Clean Architecture** with strict dependency direction: outer layers depend on inner layers, never the reverse. Domain logic has zero dependencies on FastAPI, Kubernetes clients, or LLM SDKs.

---

## Layer Overview

```
┌──────────────────────────────────────────────────────────────────────────┐
│                         Presentation Layer                               │
│                   FastAPI routes · serializers · middleware             │
├──────────────────────────────────────────────────────────────────────────┤
│                         Application Layer                                │
│              Use cases · orchestrators · DTO mapping                     │
├──────────────────────────────────────────────────────────────────────────┤
│                           Domain Layer                                   │
│     Entities · value objects · rule engine · correlation · scoring       │
├──────────────────────────────────────────────────────────────────────────┤
│                       Infrastructure Layer                               │
│   K8s client · Prometheus · Loki · OTel · LLM adapter · repositories   │
└──────────────────────────────────────────────────────────────────────────┘
```

### Dependency Rule

Source code dependencies point **inward only**:

- Presentation → Application → Domain ← Infrastructure
- Infrastructure **implements** domain-defined interfaces (ports)
- Domain knows nothing about HTTP, databases, or external APIs

---

## Diagnostic Pipeline

Every diagnosis follows a fixed pipeline. LLMs are invoked only at the final stage.

```
  ┌──────────┐    ┌─────────────┐    ┌───────────┐    ┌────────────┐    ┌───────────┐
  │ Collect  │───▶│  Correlate  │───▶│   Rules   │───▶│   Score    │───▶│  Explain  │
  │ Evidence │    │   Signals   │    │  Engine   │    │ Confidence │    │   (LLM)   │
  └──────────┘    └─────────────┘    └───────────┘    └────────────┘    └───────────┘
       │                │                  │                 │                  │
   Deterministic    Deterministic     Deterministic      Deterministic       AI only
```

| Stage | Input | Output | LLM? |
|-------|-------|--------|------|
| **Collect** | Target workload reference | Raw evidence bundle | No |
| **Correlate** | Evidence bundle | Correlated signal groups | No |
| **Rules** | Correlated signals | Structured findings | No |
| **Score** | Findings + evidence | Scored findings | No |
| **Explain** | Scored findings | Human-readable report | Yes |

## Domain Layer

The core of KubeSage. Pure Python, no I/O, fully unit-testable.

### Entities

| Entity | Description |
|--------|-------------|
| `DiagnosisRequest` | Target workload (namespace, kind, name) and scope options |
| `Evidence` | A single piece of data (Event, LogEntry, MetricSample, ResourceState) |
| `EvidenceBundle` | Collection of evidence for a diagnosis, tagged by source |
| `CorrelatedGroup` | Evidence items linked by temporal or causal relationships |
| `Finding` | A diagnostic conclusion produced by a rule |
| `ConfidenceScore` | Float 0.0–1.0 with breakdown of contributing factors |
| `ScoredFinding` | Finding + ConfidenceScore + evidence references |
| `Explanation` | Human-readable summary (generated by LLM or fallback template) |
| `Recommendation` | Actionable next steps (generated by LLM or fallback template) |
| `DiagnosisReport` | Final output: scored findings, explanations, recommendations |

All entities are Pydantic models with strict validation.

### Rule Engine

```
Rule (abstract)
├── evaluate(correlated_groups) → list[Finding]
├── name: str
├── severity: Severity
└── required_signals: set[SignalType]
```

Rules are:

- **Registered** via a rule registry (Open/Closed Principle)
- **Composed** — multiple rules can fire on the same evidence
- **Independent** — each rule is a single-responsibility unit
- **Tested** — fixture in, finding out, no network calls

Example rules:

| Rule | Signals Required | Severity |
|------|-----------------|----------|
| `CrashLoopBackOffRule` | Events, PodStatus, Logs | Critical |
| `OOMKilledRule` | Events, Metrics (memory), PodStatus | Critical |
| `PendingSchedulingRule` | Events, PodStatus, NodeStatus | Warning |
| `ProbeFailureRule` | Events, Metrics (probe), Logs | Warning |
| `ImagePullFailureRule` | Events, PodStatus | Warning |

### Correlation Engine

Links evidence items into `CorrelatedGroup` objects using:

- **Temporal proximity** — events and log entries within a time window
- **Resource identity** — same pod, container, node, or owner reference
- **Causal chains** — node NotReady → pod evicted → service endpoints missing

Correlation is deterministic and configurable (time windows, identity matchers).

### Confidence Scorer

Computes a score for each finding based on:

| Factor | Weight | Example |
|--------|--------|---------|
| Signal coverage | High | Rule requires Events + Metrics; both present |
| Signal specificity | Medium | Exact OOMKilled reason vs. generic Error |
| Corroboration | High | Multiple independent signals agree |
| Conflict penalty | Negative | Contradicting evidence reduces score |

Output: `ConfidenceScore(value=0.87, factors=[...])` with an auditable breakdown.

## Application Layer

Orchestrates use cases by composing domain services and infrastructure ports.

### Use Cases

| Use Case | Description |
|----------|-------------|
| `DiagnoseWorkload` | Full pipeline: collect → correlate → rule → score → explain |
| `CollectEvidence` | Gather evidence without running diagnostics |
| `ExplainFindings` | Generate LLM explanations for pre-computed findings |

### Ports (Interfaces)

Defined in the domain/application layer, implemented in infrastructure:

```python
class EvidenceCollectorPort(Protocol):
    async def collect(self, request: DiagnosisRequest) -> EvidenceBundle: ...

class LLMExplainerPort(Protocol):
    async def explain(self, findings: list[ScoredFinding]) -> list[Explanation]: ...
    async def recommend(self, findings: list[ScoredFinding]) -> list[Recommendation]: ...
```

This follows the **Dependency Inversion Principle** — domain defines contracts; infrastructure fulfills them.

---

## Infrastructure Layer

Concrete implementations of ports. All external I/O lives here.

### Evidence Collectors

| Collector | Source | Protocol |
|-----------|--------|----------|
| `KubernetesCollector` | Kubernetes API | client-python (async) |
| `PrometheusCollector` | Metrics | PromQL over HTTP |
| `LokiCollector` | Logs | LogQL over HTTP |
| `OTelCollector` | Traces, metrics | OpenTelemetry SDK |

Each collector:

- Implements `EvidenceCollectorPort`
- Returns normalized `Evidence` objects
- Handles timeouts, retries, and partial failures independently
- Respects RBAC — returns what it can, logs what it cannot access

### LLM Adapter

| Component | Responsibility |
|-----------|---------------|
| `LLMExplainerAdapter` | Sends structured findings to LLM; receives validated Explanation/Recommendation |
| `PromptBuilder` | Constructs prompts from ScoredFinding + evidence (never raw cluster dumps) |
| `ResponseValidator` | Validates LLM output against Pydantic schemas; rejects malformed responses |
| `FallbackRenderer` | Template-based output when LLM is unavailable |

LLM providers are swappable (OpenAI, Anthropic, local/Ollama) via a provider interface.

## Presentation Layer

FastAPI application exposing the diagnostic API.

### Endpoints (planned)

| Method | Path | Description |
|--------|------|-------------|
| `POST` | `/api/v1/diagnose` | Run full diagnostic pipeline |
| `GET` | `/api/v1/findings/{id}` | Retrieve a previous diagnosis |
| `GET` | `/health` | Liveness probe |
| `GET` | `/ready` | Readiness probe (checks upstream connectivity) |

### Middleware

- Request ID injection (correlation)
- Structured JSON logging
- OpenTelemetry trace propagation
- Error handling with consistent error response schema

## Data Flow

```
Client
  │
  ▼
POST /api/v1/diagnose  { namespace, kind, name }
  │
  ▼
DiagnoseWorkload (use case)
  │
  ├──▶ KubernetesCollector.collect()  ──▶ Evidence (events, resources)
  ├──▶ PrometheusCollector.collect()  ──▶ Evidence (metrics)
  ├──▶ LokiCollector.collect()        ──▶ Evidence (logs)
  └──▶ OTelCollector.collect()        ──▶ Evidence (traces)
  │
  ▼
EvidenceBundle
  │
  ▼
CorrelationEngine.correlate()  ──▶ CorrelatedGroups
  │
  ▼
RuleEngine.evaluate()  ──▶ Findings
  │
  ▼
ConfidenceScorer.score()  ──▶ ScoredFindings
  │
  ▼
LLMExplainer.explain()  ──▶ Explanations + Recommendations
  │
  ▼
DiagnosisReport  ──▶ JSON response
```

## Design Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Language | Python 3.12 | Ecosystem maturity for K8s, ML, and async I/O |
| API framework | FastAPI | Async-native, OpenAPI generation, Pydantic integration |
| Validation | Pydantic v2 | Strict schemas at every boundary |
| Architecture | Clean Architecture | Testable domain, swappable infrastructure |
| Diagnostic logic | Deterministic rules | Reproducible, auditable, testable |
| AI role | Explanation only | LLMs never decide; they translate |
| Observability | OTel + Prometheus + Loki | Same stack KubeSage consumes; dogfooding |
| State | Ephemeral by default | No persistent cluster data unless opted in |
| Mutations | None | Read-only platform; humans execute recommendations |

## Security

- **Credentials** — loaded from environment or mounted secrets; never logged
- **RBAC** — minimal read-only ClusterRole; graceful degradation on denied permissions
- **Data handling** — evidence processed in-memory; not persisted by default
- **LLM data** — only structured findings sent to LLM; no raw credentials or full kubeconfig
- **Network** — all upstream calls use TLS; timeouts prevent resource exhaustion

---

## Scalability Considerations

- Evidence collection runs concurrently (asyncio) with per-source timeouts
- Rule engine is CPU-bound and synchronous — suitable for process-level parallelism if needed
- LLM calls are the slowest stage — async with timeout; fallback if unavailable
- No shared mutable state — each diagnosis is independent and horizontally scalable
